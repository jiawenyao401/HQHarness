# HQHarness built-in automation

This package composes two Cordis plugins, `browser-use` and `computer-use`, and their two settings entries. It registers `browser_use` and `computer_use` with the existing Harness ToolRuntime. The current session model drives them; no second LLM key, Chrome install, Python environment or MCP server is required.

Privileged work belongs to Electron main. The package never imports Electron or depends on cwd for host package resolution. A process-local authenticated bridge is supplied only to the HQHarness child. Images are stored through Harness attachments and returned as durable image blocks.

First use requests session access. Computer Use also requires macOS screen recording and accessibility permission; Windows secure/UAC desktops are unavailable. Stop in Settings > Plugins or use Command/Control+Shift+F12 if registered. Safe Mode omits these capabilities.

See [implementation and qualification](../../docs/desktop-automation.md). The browser uses bundled Chromium; desktop input and capture use the bundled Cua Driver 0.28.0 native SDK. Computer Use supports structured application-window observations and primary-display screenshots; screenshot fallback needs a model with image input. macOS requires version 13 or newer. No separate browser-use Python agent is installed.

Between model steps, the host plugin reduces expired automation observations in the model-visible history. It keeps the latest two model steps and each capability's latest two successful observations unchanged. Older structured results are eligible only above 16 KiB with at least 8 KiB saved: expired refs and screen geometry are removed, while all semantic rows, their order and duplicates, action outcomes, URLs, verification and sequence status remain. At least four older screenshot occurrences are required for a durable image-offload batch. Original results and attachments remain in the session log, including across restart and fork. User instructions, other tools, failures and partial sequences are untouched. The maintenance uses the existing session-query, token-meter and image-offload contracts; missing optional services or a failed/stale read leave the task usable. Logs contain only counts, text-byte totals and estimated request-token totals. These estimates do not predict provider latency.
